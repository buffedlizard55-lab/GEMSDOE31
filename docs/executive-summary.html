Why it leads, and whether we can score higher

Why H33-2-B2 leads

H33 is pruning economics, not new fault discovery. Measured geometry: it equals H27 with every dot ≤2 px (≤200 m) from the public catalogue deleted — 2,545 flank dots removed, 0 added, all 35,483 dots >300 m kept. With the distance-weighted Tversky index DTI = T / (0.2·T + 0.2·F + 0.8·K) and a 300 m triangular kernel, every emitted pixel pays ~0.2 false-positive weight while truth credit saturates within the kernel. Deleting near-catalogue dots (whose kernel credit overlaps already-mapped / masked traces) cuts F faster than it loses T. Sparse, thin, off-catalogue dots therefore beat thick, dense, on-catalogue rasters (0.0009–0.19 for dense ML fills).

Can we beat 0.2778?

Only by finding new true off-catalogue traces at the same sparse budget. Every in-repo attempt (H31-E SCGP, HVDC, RBU31, MAGREST, TGJ31, CONCORD31, CSDU this session) is holdout-negative or holdout-unvalidated, so no verified path above 0.2778 exists yet. Claiming one would be fabrication. The user-reported 0.3195 / 0.4413 figures carry no organizer receipt and are flagged, not adopted as targets.

Fluid upflow is focused at stepover / relay-ramp dilation zones between en-echelon fault segments — zones with no surface trace and no USGS-catalogue entry, which catalogue-trace and LiDAR-scarp submissions both miss.

Portal workflow

How to make a submission into the contest

These are portal instructions for a future gate-passing file. No file linked here is approved; do not upload the CSDU research TIFF.

  1. Confirm approval. A candidate is ready only after its run card reports verdict = promote, holdout DTI beats the same-run incumbent on a buffered spatial holdout, fresh confirmation passes, the registry uniqueness gate passes, and a separate selector has authorized the slot (weekly cap applies). Today nothing meets this.
  2. Download the approved file. Get the single-band GeoTIFF, or a .zip containing exactly one GeoTIFF — not a report, run-card JSON, feature stack, or multi-file ZIP. Verify its SHA-256 against the format receipt before upload.
  3. Open your own DrivenData submission page. drivendata.org/competitions/306/competition-doe-gems/, sign in, accept the rules, and check your remaining weekly quota. This project does not know or spend your quota.
  4. Select the file under “File to submit”. It must match the submission format’s CRS, shape, and geotransform (EPSG:32611, 3730×3292, 100 m). Use the all-finite (zeros-outside) encoding if the portal evaluates the whole array — this prevents the “Predicted values must be in range [0, 1]” error.
  5. Paste the note (at most 140 characters) generated with the candidate into “Note (optional)” — e.g. for clustering with k=25 — then submit. Keep the organizer’s receipt, exact SHA-256, name, and reported result together. Until that receipt exists, no result is organizer-confirmed.

Range-error prevention

No silent clipping. No hidden NaN inside the footprint. Read-back validation before download: one float32 band; exact CRS/shape/transform; finite footprint values in [0,1]; outside-mask encoding; hash; one-TIFF ZIP roundtrip. python scripts/validate_submission.py <candidate.tif> --template data/sample_submission.tif --convention all-finite

What cannot be inferred

The portal implementation is private. An error message alone does not identify its cause. Local validation is automated, not delegated to a human inspector, but it cannot prove organizer acceptance or settle the outside-footprint rule. Entrant identity, rules, final-slot selection, and portal upload are outside this software.
